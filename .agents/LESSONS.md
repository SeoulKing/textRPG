# Project Lessons

다음 작업의 도구 선택을 바꾸는 항목만 유지합니다.

| 범위 | 관찰 또는 실패 지문 | 다음 결정 | 재검토 조건 |
| --- | --- | --- | --- |
| Content Studio runtime source | Published Studio data can come from the configured database and differ from the tracked `content/content-studio.json` seed. | Test Studio synchronization with an injected or loaded published registry; do not treat the local seed as evidence of the live value. | Reconsider when deployment no longer uses `PostgresContentStudioStore` or published data is exported back into the tracked seed. |
| 사용자 선호 | 실패한 방법을 반복하면 토큰과 시간이 낭비됩니다. | 같은 실패 지문은 전제 조건 변화 없이 재시도하지 않고, 필요한 최소 검증만 수행합니다. | 사용자가 더 강한 검증이나 재시도를 명시적으로 요청할 때 |
| 재고 노드 설계 | 사용자는 내용물이 비어도 남는 보관함과, 모두 수집하면 장소·진입 선택지가 사라지는 더미를 서로 다른 종류로 봅니다. | 보관함은 `depletionBehavior: "remain"`을 유지하고, 소진 시 사라질 더미에만 `"disappear"`를 지정합니다. | 사용자가 재생성·리필되는 세 번째 재고 노드 유형을 요구할 때 |
| 시스템 노트 | 아이템 획득 칩은 기존 게임 문법인 `+수량 아이템명` 순서를 사용하며, 문자열 조립 대신 `systemNoteEntries`의 `item` delta로 저장해야 초록색 칩과 현재 아이템명을 일관되게 적용할 수 있습니다. | 노트는 현재 `.scene-story-block` 안에서 서사의 끝과 16px 간격으로 배치해 스크롤용 최소 높이가 노트를 밀어내지 않게 합니다. 보상 시스템 노트는 중앙 포매터를 통해 `+1 캔 음식 / +1 진통제`처럼 만들고 `+캔 음식 1개`나 `캔 음식 1개` 같은 자유 문자열을 새로 만들지 않습니다. | 사용자가 시스템 노트 표기 규칙 자체를 변경할 때 |
| NPC 선택 후 서사 | 사용자는 두 문단을 `첫 문단=행동`, `둘째 문단=배경`처럼 고정하면 단조롭게 느낍니다. | 두 문단 모두 플레이어의 말·행동·시선·거리·사물·소리를 장면에 맞게 섞고 선택지마다 순서와 호흡을 바꿉니다. 단, NPC의 새 반응은 다음 `npc_reply` 역할에 남깁니다. | 사용자가 대화 서사의 문단 수나 역할 분담을 다시 지정할 때 |
| Git 게시 | 기존 Git HTTPS 인증을 사용합니다. 사용자 배포 대상은 `render.yaml`의 `codex/region-content-structure`이며, 기본 브랜치 `master`나 현재 작업 브랜치가 배포 대상이라고 추정하면 안 됩니다. | 푸시 전에 배포 목적과 설정의 대상 브랜치를 확인합니다. 실제 프로젝트 변경만 명시적으로 스테이징하고 런타임 로그는 제외합니다. 배포 요청은 기존 배포 브랜치에 이력을 보존해 반영하고 푸시하며, 별도 브랜치 푸시만으로 배포됐다고 보고하지 않습니다. PR은 명시 요청 때만 생성합니다. | 배포 설정 또는 사용자가 지정한 대상 브랜치가 바뀌거나 HTTPS Git 인증이 실패할 때 |
| 로컬 콘텐츠 검증 | 현재 셸에서는 Node와 npm.cmd가 실행되지만, tsx는 여전히 uv_os_get_passwd returned ENOMEM으로 중단됩니다. tsc로 컴파일한 콘텐츠 검증과 Node 내장 테스트는 정상 실행됩니다. | PATH 복구만을 재시도 조건으로 삼지 않습니다. .tmp-validate 아래로 필요한 TypeScript 테스트를 컴파일해 node --test로 실행하고, 서버 반영은 기존 build 산출물을 사용합니다. | 런타임이 바뀌고 node:os의 userInfo() 호출이 정상 동작함을 확인했을 때 |
| 브라우저 검증 | 현재 `package.json`에는 Playwright 의존성이 없어 독립 Playwright 스크립트가 `ERR_MODULE_NOT_FOUND: playwright`로 실패하고, Chrome headless/CDP는 관리형 셸의 프로세스 권한과 페이지 타깃 시작에 좌우됩니다. 반면 Codex의 열린 인앱 브라우저는 Browser 플러그인의 `browser-client`로 연결·조작·실측이 확인되었습니다. | 사용자가 열어 둔 로컬 화면 검증은 인앱 브라우저 탭을 연결해 새로고침하고, 내장 Playwright API로 DOM·치수·화면을 한 세션에서 확인합니다. 독립 Playwright나 Chrome 프로세스를 관성적으로 재호출하지 않습니다. | 인앱 브라우저 연결 자체가 실패하거나 사용자가 Chrome/독립 실행 환경을 명시할 때 |
| 모바일 기준 해상도 | 사용자는 이 게임을 모바일 중심으로 설계하며 갤럭시 S24 울트라 기준의 `384 × 824` CSS 픽셀을 기본 화면 크기로 지정했습니다. | 별도 해상도 요청이 없으면 UI 구현과 인앱 브라우저 검증을 `384 × 824` 뷰포트에서 우선 수행하고, 더 좁은 화면에서도 가로 넘침이 없는지 함께 고려합니다. | 사용자가 새로운 기준 기기나 해상도를 지정할 때 |
| 장면 그래픽 방향 | 기존 거처는 생활형 16비트 픽셀 디오라마 방향이며, 사용자는 숲 장소 이미지를 《디스 워 오브 마인》 분위기의 연필 스케치·목탄 그림으로 교체하기로 확정했습니다. | 후속 장소 이미지 교체 시 `assets/scenes/forest-pencil-charcoal.png`를 새 화풍의 기준으로 참고합니다. 기존 거처의 픽셀 애니메이션은 별도 변경 요청 범위에 따라 판단합니다. | 사용자가 다른 화풍을 선택하거나 장소별 스타일을 따로 지정할 때 |
| 로컬 Gemini 연결 | 서버는 시작할 때만 `.env`와 `.env.local`을 읽으므로 실행 후 키를 추가·변경하면 기존 프로세스에는 반영되지 않습니다. 또한 관리형 기본 샌드박스에서 띄운 Node 서버의 외부 `fetch`는 `cause.code: EACCES`로 차단될 수 있지만, 동일 설정을 네트워크 권한으로 실행하면 Gemini 모델 조회와 생성이 정상 동작합니다. | `.env` 변경 시 3000번 포트의 기존 서버를 재시작하고, 기본 실행의 Gemini 테스트가 `fetch failed`이면 Node 단발 연결의 `cause.code`를 확인합니다. `EACCES`일 때만 서버를 네트워크 권한이 있는 숨김 프로세스로 다시 띄운 뒤 `/api/gemini/test` 실제 생성 성공으로 판정합니다. | 서버가 `.env`를 런타임에 다시 읽도록 바뀌거나 관리형 기본 샌드박스에 외부 네트워크 권한이 제공될 때 |
| 로컬 서버 재시작 | 관리형 PowerShell의 `Start-Process`는 `Path`/`PATH` 중복, `Stop-Process`는 NullReference 오류 또는 종료 지연이 발생할 수 있습니다. | 새 빌드를 만든 뒤 정확한 3000번 리스너 PID와 실행 명령을 확인합니다. `Stop-Process`가 실패하면 해당 PID가 여전히 Node 리스너인지 확인한 뒤 `.NET Process.Kill()`과 `WaitForExit()`를 사용합니다. 포트 해제 후 Node `child_process.spawn`의 `detached: true`, `windowsHide: true`와 `.runtime` 로그로 같은 서버를 다시 실행하고, 실제 API 응답으로 확인합니다. | PowerShell의 해당 오류가 해소되거나 서버가 `tsx watch`처럼 자동 재시작 방식으로 실행될 때 |
| 신규 지역 발견 상태 | 위치를 레지스트리와 이웃 링크에만 추가하면 기존 저장에서는 `known_<locationId>`가 없어 지도에서 숨겨질 수 있습니다. | 새 고정 지역을 추가할 때 `normalizeExplorationKnowledge`의 발견 조건과 기존 저장에서 이를 다시 계산하는 경로를 함께 확인합니다. | 지도 노출이 발견 플래그를 사용하지 않도록 구조가 바뀔 때 |
| LLM 선택 후 서사 중복 | 지하철 `postChoiceNarrative`는 클라이언트가 즉시 표시한 뒤 결과 LLM에도 문맥으로 전달하므로, LLM이 이를 다시 출력하면 새 장면을 이어 붙일 때 같은 문장이 두 번 보입니다. | 결과 장면 저장 전과 기존 장면 표시 시 직전 `postChoiceNarrative`를 문장 단위로 제외하고, 프롬프트에도 이미 표시된 문장을 반복·인용·의역하지 않도록 명시합니다. | 선택 직후 서사를 클라이언트에서 선표시하지 않거나 결과 LLM 입력에서 제거할 때 |
| 선택지 UI | 사용자는 대피소 시안을 확인한 뒤 표형 선택지의 공통 적용을 승인했습니다. 서사와 같은 배경, 행 사이 간격 없음, 얇은 구분선, 왼쪽 선택 문구·오른쪽 효과 설명을 선호합니다. | 모든 일반 게임 선택지에 공통 스타일을 사용하고 긴 문구·설명은 잘리지 않게 줄바꿈합니다. 새 디자인 방향을 시험할 때는 한 화면에서 먼저 비교합니다. | 사용자가 다른 디자인을 요청할 때 |
| 장소 내 서사 연속성 | 사용자는 같은 장소에서 물건 앞으로 이동하거나 행동할 때 본문을 지우지 않고, 이전 서사가 위로 올라가는 움직임과 함께 새 서사의 첫 줄이 화면 상단에 놓이길 원합니다. | 같은 장소의 새 장면은 이전 문단에 이어 붙이고 스크롤로 상단에 맞춥니다. 이전 문단은 위로 스크롤해 읽을 수 있게 남기고, 타이핑 건너뛰기는 현재 블록만 완성합니다. 본문 오른쪽의 기본·일시 표시 스크롤 막대는 숨기되 스크롤 동작은 유지합니다. | 사용자가 대화·행동별로 본문을 나누거나 장소 간에도 서사를 잇도록 요청할 때 |
| 기존 저장의 콘텐츠 수정 | 사용자는 삭제한 요리와 통합한 재료가 기존 게임에도 즉시 반영되기를 기대합니다. 새 게임과 Studio 데이터만 바꾸면 저장에 고정된 콘텐츠 버전이 옛 목록을 되살립니다. | 명시적 삭제·통합은 런타임 레지스트리에서 적용해 목록·조건·실제 효과·재료 획득 경로를 함께 맞춥니다. 보관된 버전 원본과 플레이 진행은 유지하고, 옛 저장을 불러오는 테스트를 포함합니다. | 사용자가 특정 저장에 구버전 규칙을 유지하라고 명시할 때 |
