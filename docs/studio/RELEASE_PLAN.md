# 아르카나 출시 로드맵

이 문서는 Codex 제작 조직이 향후 작업을 선택할 때 사용하는 출시 방향과 단계별 인수 기준입니다. 첫 출시는 **기존 아르카나를 재사용한 10~15분 핵심 체험 공개 시범판**으로 제안드립니다. 전체 온라인 RPG의 완성이나 공개 운영 승인으로 해석하지 않습니다.

현재 상태는 **출시계약 초안 전달, M1 이후 제작 승인 대기**입니다. 작업 원장의 M0는 운영 구축과 이 초안의 정적 인수를 뜻하며, 아래 제품 방향·수치·검증 권한은 해당 목표의 사용자 승인으로 별도 확정합니다. 이 문서를 작성하기 위해 소스·참조만 확인했으며 테스트·게임·브라우저·빌드를 실행하지 않았습니다. 아래의 시간·동선·승인 요청은 제작 제안입니다. 승인된 캐릭터·미술·기존 저장을 바꾸는 근거가 되지 않습니다.

## 1. 첫 출시 계약과 범위

### 플레이어에게 전달할 경험

분수 광장에서 주인공을 움직이고, 여관에서 대표 의뢰를 받은 뒤, 슬라임 전투와 스킬 사용을 경험하고 돌아와 보상을 받으시도록 구성합니다. 이어 강변에서 낚시와 소지품 변화를 경험하고, 재접속으로 진행 보존을 확인할 수 있는 흐름을 제안드립니다.

| 순서 | 체험 목표 | 재사용 대상 | 계획 상태 |
| --- | --- | --- | --- |
| 1 | 광장에 도착하여 이동·방향 전환·상호작용을 익히십니다. | 분수 광장, 하이브리드 버전 1, 기존 입력·HUD | 소스 기준 있음 · 체감 미검증 |
| 2 | 여관 퀘스트판에서 마르텐의 슬라임 퇴치 의뢰를 받으십니다. | 기존 여관·대화·의뢰 ID | UI·규칙 소스 기준 있음 · 온라인 처치 연결 필요 |
| 3 | 슬라임을 상대하며 기본 주문과 회피, 성장 표시를 경험하십니다. | 기존 온라인 전투·스킬·슬라임 자산 | 전투 소스 기준 있음 · 보상·성장 정합성 확인 필요 |
| 4 | 마르텐에게 보고하여 의뢰를 마무리하십니다. | 기존 보고·보상·의뢰 화면 | 소스 기준 있음 · 전 구간 미검증 |
| 5 | 강변에서 낚싯대를 장착하고 낚시를 하신 뒤 소지품을 확인하십니다. | 기존 강변·낚시·아이템·숙련도 | 소스 기준 있음 · 동선·가독성 미검증 |
| 6 | 체험을 마치고 재접속하여 의뢰·소지품·위치가 보존되는지 확인하십니다. | 기존 계정·온라인 저장·복원 | 저장 소스 기준 있음 · 시범판 인수 미검증 |

- 10~15분은 최초 목표 시간이며 측정 결과가 아닙니다. 기존 10마리 의뢰와 낚시 난도가 이 시간에 맞는지는 승인된 플레이 확인으로 판단합니다. 시간을 맞추려고 처치 수·보상·재생성·성장값을 임의로 변경하지 않습니다.
- 의뢰는 `arcana_inn_slimes` 한 개를 대표로 삼는 안입니다. 별도 새 의뢰·새 보스·새 인물을 추가하지 않는 구성을 기본값으로 제안드립니다.
- 강변 낚시는 대표 의뢰 이후 생활 경험으로 배치하는 안입니다. 낚시 성공을 의뢰 완료 조건에 몰래 추가하거나, 기존 완료 저장을 초기화하지 않습니다.
- 기존 캐릭터는 현재 진행을 보존합니다. 초기 체험 인수에는 승인된 별도 검증 캐릭터를 사용하며, 기존 사용자 캐릭터를 초기화하지 않습니다.
- 목표 플랫폼은 기존 `/godot/` 웹 제공 경로와 모바일 세로 화면·데스크톱 입력을 유지하는 안입니다. 지원 기기·브라우저 목록과 공개 접속 인원은 M0에서 승인받아 확정합니다.

### 첫 시범판에서 제외할 범위

대규모 온라인 운영, 서버 증설·동시접속 확대, 경제 시스템 재설계, 새 지역·던전·보스·파티·PvP, 전체 본편 서사, 모든 스킬·궁극기·생활 콘텐츠 완성을 첫 시범판의 필수 조건으로 삼지 않습니다. 기존 기능을 삭제하라는 뜻은 아니며 새 작업을 배정하지 않는다는 뜻입니다.

주인공 교체, 새 렌더러·엔진 전환, 기존 계정·저장 ID 변경, 수동 배치 재생성, 미승인 새 미술 제작, 새 유료 서비스 도입도 범위에 포함하지 않습니다. Git 게시·공개 배포·공개 DB 변경은 각각의 명시적 실행 승인으로 다룹니다.

## 2. 현재 근거와 남은 연결

`소스 기준 있음`은 파일과 호출·참조가 확인되었다는 뜻입니다. 게임에서 정상 동작하거나 출시 품질을 만족한다는 뜻은 아닙니다. `연결 필요`는 구성 요소 사이의 차이나 인계 작업이 확인된 상태이고, `미검증`은 실행·체감 확인의 증거가 없는 상태입니다. `미구현`은 아래 출시 기획에서 새로 만들기로 제안하는 부분을 가리키며 기존 게임 전체에 대한 부재 판정은 아닙니다.

### 먼저 해결해야 할 실제 불일치

- **처치 보상·의뢰 집계:** `src/game/arcana-economy.ts`는 점액질 1개, 의뢰 수락 뒤 10마리 집계, 여관 보고 보상 10골드를 정의합니다. `src/game/arcana-spatial.ts`도 점액질 보상을 전달합니다. 반면 현재 `src/online/combat.ts`는 처치당 30골드를 직접 더하고 해당 온라인 전투 경로에서 `awardSlimeLoot`를 호출하지 않습니다. 두 경로를 같은 것으로 간주하지 않고 활성 온라인 경로의 연결을 P0로 다룹니다. 최신 역할 문서의 수치와 실제 코드가 다르므로 수정 기준은 M0에서 잠그고, 미승인 밸런스 변경으로 처리하지 않습니다.
- **성장 규칙:** 개발 역할 문서의 유효 기여량 성장 설명과 현재 온라인 파이어볼 명중 10XP, 별도 파이어볼 성장 기술 문서 사이에 차이가 있습니다. 로직·표시·이전 저장의 호환 범위를 함께 확인해 M0 결정 기록에 남깁니다. 이 로드맵에서 새 수치나 성장 체계를 확정하지 않습니다.
- **확정 외형과 동작 완료:** 주인공 디자인 확정은 모든 방향·동작·낚시 자세의 시각 인수를 의미하지 않습니다. 기존 원본·사용자 편집값을 보존하며 부족한 동작만 작업으로 나눕니다.

### 사용자 추가 우선 목표 — 요리와 음식

2026-11-05 사용자 지시로 **M0 → M0-COOK 요리·음식 → M1 → M2 → M3 → M4** 순서를 등록했습니다. 기존 목표 ID는 유지하며 상세 범위와 완료 조건의 원본은 board.json의 M0-COOK에 둡니다.

현재 src/online/life.ts에는 모닥불 제작·설치, 생선 굽기, 품질별 음식, 허기 회복·감소와 요리 숙련도가 있고, world.ts·routes.ts 및 Godot life.gd에 연결되어 있습니다. 이는 소스 기준 확인이며 플레이 검증 결과는 아닙니다. 이 기반을 보존해 재료·레시피·조리·섭취·효과를 확장하는 안을 첫 범위로 제안합니다. 음식 수·새 효과 수치·허기의 추가 규칙은 아직 확정하지 않았습니다.

첫 작업은 COOK-010의 제작 계약 구체화입니다. 목표 등록 뒤 상세 범위를 정리하며, 시범판의 기존 10~15분 동선·체험 시간은 이 목표의 범위에 맞춰 다시 검토합니다.

## 3. 단계별 제작과 완료 조건

각 단계는 제작 결과, 독립 검토, 필요한 사용자 판단을 모두 충족해야 닫습니다. 자료가 없으면 `확인 대기`로 남기고 다음 단계의 독립 작업만 이어갑니다. 이 표는 목표 순서이며 완료 보고나 일정 약속이 아닙니다.

| 단계 | 목표와 주요 산출물 | 완료 조건 | 최종 사용자 판단 |
| --- | --- | --- | --- |
| **M0 운영·출시계약** | 현재 작업본 보존 기준, 운영 규칙·역할·작업 원장, 시범판 동선·제외 범위, 보상·성장 결정 목록, 허용 검증·시간/회차 예산을 정리합니다. | 기존 변경 소유권과 보호 자산을 확인하고, P0 의존성·담당·인수 기준·승인 대기를 작업 원장에 연결합니다. 도구가 없는 작업의 대체·보류 경로를 정합니다. | 10~15분 시범판 방향, 대표 의뢰, 지원 범위, 수치 기준, 자동 검증 권한과 운영 예산을 승인해 주십니다. |

| **M1 대표 공간·주인공** | 기존 광장·강변의 한 동선과 확정 주인공의 이동·정지·방향 전환을 다듬습니다. | 원본·Transform·ID를 보존하고 출입·점유·충돌·가림·동작의 결과와 미확인을 인계합니다. 새 미술이 필요하면 승인 범위 안에서만 제작합니다. 승인된 시각/플레이 확인 전에는 체감 완성으로 닫지 않습니다. | 대표 공간의 구도와 밀도, 주인공 동작, 새 디자인이 있으면 해당 시안을 판단해 주십니다. |

| **M4 이후 본편 범위 확정** | 시범판 피드백·결함·제작 비용을 근거로 다음 장과 전체 본편의 끝을 정의합니다. | 이후 지역·서사·성장·생활·온라인 규모별 필수/선택 범위를 나누고, 본편 종료 조건과 후속 마일스톤을 별도 출시계약으로 확정합니다. | 무엇을 추가하고 무엇을 끝낼지 승인해 주십니다. M4 계약 전에는 조직이 전체 RPG 규모를 자동 확장하지 않습니다. |

## 4. 우선 작업과 조직 간 인계

### P0 — 진행·인수·공개를 막는 작업

1. **보존 기준과 권한을 잠급니다.** 현재 대량 미커밋 변경·미추적 자산·사용자 수동 원본을 보존할 기준을 확보하고 작업 소유권을 나눕니다. 새 worktree가 현재 변경을 자동 포함한다고 가정하지 않습니다. 담당은 제작 총괄이며 개발·아트가 자기 보호 대상을 전달합니다.
2. **대표 의뢰의 활성 온라인 경로를 맞춥니다.** 기획이 승인 기준을 전달하고 개발이 처치→집계→보고·보상→저장을 연결하며 서사가 안내를 맞춥니다. 통합·QA는 중복 보상과 기존 저장 영향을 제작 컨텍스트와 분리해 검토합니다.
3. **성장 규칙의 차이를 결정 요청으로 묶습니다.** 새 밸런스를 임의 채택하지 않고 실제 활성 로직, 역할 문서, 기존 저장의 차이와 수정 영향을 한 번에 제시합니다.
4. **대표 동선의 차단 결함을 먼저 처리합니다.** 광장·여관·전투·강변의 접근, 상호작용 대상, 조작 충돌과 다음 행동 안내를 확인할 작업을 배정합니다. 실행이 허용되지 않은 부분은 미검증으로 남깁니다.
5. **저장·취소·복원의 인수 경로를 준비합니다.** 실사용 계정 대신 승인된 검증 범위를 지정하고 의뢰·보상·낚시·전투 결과가 어떤 저장 경로를 거치는지 연결합니다.
6. **M3 이전 공개 조건을 잠급니다.** 대상 환경·공개 인원·운영 저장·복구·패키징·검증 권한이 정해지지 않으면 공개 준비 완료로 판정하지 않습니다.

### P1 — P0 이후 체험 품질을 높이는 작업

- 확정 주인공의 이동·접지·방향 전환과 실제 체험에 필요한 동작을 좁혀 보정합니다.
- 승인 가로등·분수와 기존 소품을 재사용해 대표 구역의 가독성·동선·가림을 개선합니다.
- 여관 대화·의뢰 표시·강변 접근 안내를 서사와 UI에서 함께 다듬습니다. 강제 시작 팝업을 새 기본값으로 만들지 않습니다.
- 낚싯대·찌·포획 조작·소지품·성장 표시가 모바일에서도 읽히도록 정리합니다.
- 승인된 플레이 확인 뒤 실제 체험 시간과 막힌 지점을 근거로 다음 작업을 고릅니다. 새 콘텐츠 양을 기본 성과 지표로 삼지 않습니다.

제작 총괄은 목표와 우선순위·작업 상태를 관리합니다. 제작 역할은 입력 원본·변경 결과·실제 연결·증거·미확인을 전달하고, 통합·QA는 인수 조건을 직접 대조합니다. 같은 파일뿐 아니라 원본·관련 씬·등록·생성 산출물 묶음의 동시 수정도 피합니다. 역할별 상세 규격은 [개발](../roles/DEVELOPMENT.md)·[캐릭터](../roles/CHARACTER_ART.md)·[월드](../roles/WORLD_BUILDING.md)·[서사](../roles/NARRATIVE.md)를 참조하며 이 문서에 복제하지 않습니다.

## 5. 디자인·검증 승인 초안과 인수

### 신규 디자인 시안 목록

기본안의 새 디자인 필수 수는 **0개**로 제안드립니다. 승인된 광장·강변·주인공·NPC·슬라임·아이템과 기존 UI를 먼저 사용합니다. 다음 항목은 필요성이 확인될 때만 시안을 요청하는 후보이며 제작 승인 상태가 아닙니다.

| 후보 | 시안이 필요한 조건 | 현재 상태 |
| --- | --- | --- |
| 대표 의뢰·강변의 새 표식 또는 길 안내 소품 | 기존 의뢰 마커·문·상호작용 안내 재사용으로 다음 행동을 전달하지 못하실 때 요청드립니다. | 필요성 판단 대기 · 새 미술 제작 미승인 |
| 시범판 시작·마무리 표현 | 기존 게임 진입·의뢰 완료·메뉴 안내만으로 체험의 목적과 마무리를 전달하기 어려우실 때 UI안을 요청드립니다. | 필요성 판단 대기 · 신규 화면 미구현으로 계획 |
| 새 캐릭터 그림·낚시/시전 프레임 | 기존 승인 파츠·동작을 보정하는 범위로 해결할 수 없고 새 그림이 실제로 필요할 때 요청드립니다. | 필요성 판단 대기 · 확정 외형 유지 · 새 미술 제작 미승인 |

새 외형이 필요하면 해당 스킬과 역할 문서의 컨셉 한 장→사용자 승인→제작 공정을 따릅니다. 이미 승인된 외형의 재사용과 단순 오류 수정에는 승인을 반복 요청하지 않습니다.

### 목표별 허용 검증 초안

아래는 앞으로 승인받을 제안입니다. 현재의 기본 권한은 파일·참조·필요한 구문 확인까지이며 **이 문서만으로 테스트·브라우저·게임·빌드를 허용하지 않습니다.** 사용자가 특정 목표의 검증을 승인하시면 해당 범위와 조건을 작업 원장에 기록하고 반복해서 묻지 않습니다.

| 목표 | 기본 수행 가능한 확인 | 사전 위임을 제안드리는 최소 검증 | 현재 상태 |
| --- | --- | --- | --- |
| M0 운영·출시계약 | 문서 경로·원장·권한·상태 일관성을 확인합니다. | 코드·게임 실행은 필요하지 않습니다. | 정적 문서 확인만 허용 |
| M1 공간·주인공 | 원본·씬 참조·배치·ID·수정 범위를 확인합니다. | 승인된 후보의 정지 렌더·동작 비교와 대표 장면 1회 플레이를 제안드립니다. | 실행·시각 인수 권한 대기 |
| M2 의뢰·전투·스킬 | 활성 서버/클라이언트 경로와 저장 영향, 필요한 구문을 확인합니다. | 변경과 직접 연결된 기존 테스트를 선택하고, 타입 경계를 바꿀 때만 `npm.cmd run typecheck`를 추가합니다. 격리된 캐릭터로 대표 동선을 한 세션에서 확인하는 안입니다. | 테스트·플레이 권한 대기 |
| M2 낚시·저장 | 장착·물 영역·상태 전이·지급·체크포인트 연결을 확인합니다. | 동일 인수 세션에 낚시 실패/취소·성공과 재접속을 묶는 안입니다. 공개 DB·실사용 저장은 쓰지 않습니다. | 테스트·플레이·검증 데이터 범위 대기 |
| M3 패키징·공개 인수 | 소스와 export preset·포함 경로·기존 제공 설정을 대조합니다. | 산출물 생성에 필요한 Godot 내보내기와 서버 패키징, 승인된 대상 환경의 핵심 동선 1회 확인을 제안드립니다. 검증만을 위한 새 의존성은 설치하지 않습니다. | 빌드·배포 대상 실행 권한 대기 |

콘텐츠 정의를 실제로 변경하는 작업에는 승인 범위에 맞춰 `npm.cmd run content:validate`를 우선 선택합니다. 기존 검증이 같은 위험을 충분히 다루면 추가 검증을 연속 실행하지 않습니다. 같은 실패는 도구·대상·핵심 오류로 식별하고 성공 전제가 바뀌었을 때만 한 번 재시도합니다.

### 최종 사용자 인수

시범판의 최종 인수에서는 아래 네 가지를 판단해 주십니다. 통합·QA의 증거와 알려진 문제를 함께 전달하며 실행하지 않은 항목은 미확인으로 남깁니다.

- **방향:** 확정 주인공과 대표 공간이 앞으로 확장할 아르카나의 기준으로 적절하신지 판단해 주십니다.
- **플레이:** 대표 의뢰·전투·생활 경험이 하나의 흐름으로 이해되고 조작·반복량·난도가 적절하신지 판단해 주십니다.
- **보존:** 기존 캐릭터와 수동 원본을 보존하고, 승인된 검증 캐릭터의 진행·보상·재접속 결과가 일관되는지 확인해 주십니다.
- **공개:** 현재 품질과 알려진 제약으로 어느 대상에게 공개할지 승인해 주십니다. 공개 이후 관찰과 복구 책임을 확정한 뒤 M4 본편 계약으로 넘어갑니다.
