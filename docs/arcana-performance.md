# 아르카나 통신·로딩 최적화

기준: `codex/region-content-structure`. 아래는 코드 변경과 확인 방법이며 실측 결과가 아닙니다.

## 적용한 변경

- `arcana_spatial.gd`: 일반 위치 동기화 간격 0.1초 → 0.25초. 입력 큐의 공격·회피·순간이동과 일시정지 전환은 이 간격을 기다리지 않습니다. 진행 중인 요청은 취소하지 않고 순서를 보존합니다. 일반 동기화 시도 상한은 초당 약 10회에서 4회로 줄지만 실제 빈도는 응답 시간에 좌우됩니다.
- `service.ts`: 공간 전투에서 게임 상태만 복제하고 변경하지 않는 월드 카드 복제를 생략합니다. 미저장 변경 여부를 추적하여 이미 저장된 상태를 자동 저장 타이머나 일반 행동 전환이 다시 쓰지 않게 합니다. 공격·보상·승패·일시정지 저장과 기존 1초 체크포인트는 유지합니다.
- `server.ts`: Godot JS/WASM/PCK 파일은 캐시를 저장하되 매번 ETag/Last-Modified로 재검증합니다. 파일명이 고정되어 있으므로 장기 immutable 캐시를 사용하지 않습니다. HTML과 API는 no-store를 유지합니다.
- `build-godot-delivery.mjs`: 서버 빌드 때 Godot 내보내기 파일과 gzip 파일을 `.server-dist/godot`에 함께 생성합니다. production 서버는 이 사본을 제공하고 개발 서버는 `godot-web`을 사용합니다. 압축은 요청마다 수행하지 않습니다. 이는 전송량 최적화이며 원본 PCK/WASM 크기 감소는 아닙니다.

## 계측 읽기

- 기존 `window.render_game_to_text()` 결과의 `timing`: FPS, p95 프레임 시간, 최대 프레임 시간, 드로우콜.
- 같은 결과의 `networkTiming`: 누적 요청·실패 수, 마지막 HTTP 요청 시간, 최근 최대 100개 요청의 p95. 클라이언트 관측 시간이므로 네트워크·서버 대기·본문 수신을 포함하며 순수 네트워크 왕복 시간이 아닙니다. 재시도는 각각 집계합니다.
- 행동 API의 `Server-Timing` 및 서버 `game action latency` 로그: 전체 처리, 큐 대기, 상태 로드, 복제, 규칙 계산, 저장, 응답 객체 구성 시간. 공간 전투 로그의 `saved`로 저장 여부를 구분합니다. snapshot 시간에는 JSON 직렬화·전송이 포함되지 않습니다. 기존 비공간 행동의 load/rules 계측은 시작 이후 누적 시간일 수 있으므로 공간 전투와 직접 합산하지 않습니다.

## 반영과 직접 확인

1. Godot 원본을 먼저 웹 내보내기한 뒤 서버 빌드를 실행해야 최신 클라이언트가 배포 사본에 들어갑니다. 서버 빌드는 Godot 내보내기를 대신하지 않습니다. 공개 배포에는 두 산출물이 모두 필요합니다.
2. 동일 장면에서 첫 공격·반복 공격·이동 중 회피를 비교합니다. 공격 연출은 즉시 시작하고 HP/MP·보상은 서버 확정 결과를 따라야 합니다. 위치 동기화 간격이 늘어 이동 보정이 눈에 띄는지는 실제 확인이 필요합니다.
3. 전투 중과 승리 후 다시 접속하여 진행 유지와 보상 중복 여부를 확인합니다. 서버 중단 시 최근 미저장 위치가 손실될 수 있는 기존 체크포인트 범위는 변경하지 않았습니다.
4. 캐시를 끄지 않은 브라우저에서 재접속하여 변경 없는 파일의 304 응답 또는 캐시 사용, 첫 요청의 `Content-Encoding: gzip`, `Vary: Accept-Encoding`을 확인합니다.
5. 모바일 30FPS 목표는 약 33.3ms, 60FPS 목표는 약 16.7ms 프레임 예산으로 구분합니다. 평균 FPS와 p95를 함께 봅니다.

GPU 워밍업 순서, 그림자·해상도·이펙트 품질, 리소스 분할, 타이핑 연출은 이번 변경에 포함하지 않습니다. 서버 지연과 프레임 저하를 위 계측으로 구분한 뒤 해당 병목만 조정합니다. 서버 이전이나 요금제 변경은 하지 않습니다.
