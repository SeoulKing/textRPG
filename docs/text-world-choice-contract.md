# 탐색 선택지의 표시와 실행 일관성

## 확인한 오류

편의점에서 빵을 수집한 뒤 ‘빵을 꺼내 손에 든다’를 선택하면 실행 서버가 거부했다. 물건을 드는 규칙은 충족했지만, 후보 목록을 다시 선정하면서 표시된 ID가 실행 시 목록에서 빠졌다.

운영 저장소는 `state_payload`를 PostgreSQL JSONB로 저장한다. 종전 선택지 지문은 객체 내부 키를 정렬하면서도, 객체에서 만든 후보·관찰 목록의 순서는 그대로 사용했다. 저장 후 물건의 순서만 달라져도 새로운 상황으로 판정했고, 최근 표시한 선택지에 감점을 주는 로직이 빵 대신 쌀을 골랐다. 동일한 revision에서 화면과 실행 목록이 달라질 수 있었다.

키 순서를 재정렬하는 저장소 모사로 동일 오류를 재현했다. 실제 운영 데이터나 실제 Gemini 호출은 사용하지 않았다.

## 규칙과 책임

1. 엔진과 행동 후보 생성기가 소지 수량·손 상태·접근·용기 상태 등 실행 조건을 검사한다. 물건 조작 후보는 엔진의 모의 실행도 통과해야 한다.
2. Choice Director가 현재 관심 대상과 위험도, 행동 계열별 슬롯에 따라 표시할 후보를 고른다.
3. 동일한 상황 지문이면 기록된 선택 ID와 순서를 재사용한다. LLM은 그 ID의 표현과 독백만 작성한다.
4. 실행 시 같은 후보 생성·선정 경로를 거치며 `optionId + revision`을 검사한다. 중복 클릭과 존재하지 않는 ID를 계속 거부한다.

## 수정

- 후보는 ID 순, 관찰 단계와 발견 ID는 집합의 정렬 순서로 비교한다. 객체 키나 후보 나열 순서만 바뀌면 기존 선택지를 유지한다.
- 동점 후보와 여러 위험 대상도 ID를 기준으로 일정하게 결정한다.
- 실제 행동 묶음의 순서는 정렬하지 않는다. 접근 → 열기 → 수집처럼 실행 순서가 달라지거나 실제 후보·상황이 달라지면 지문도 달라진다.
- 제한을 무시하는 실행 예외는 추가하지 않는다. 이동·발견·소모와 기존 저장 진행도 유지한다.

## 검증

`text-world-choice-contract.test.cjs`는 객체 키를 두 가지 순서로 저장·복원한 후 표시 ID, 장면 내 ID, 재조회 ID, 실행 ID의 일치를 검사한다. 편의점 19개, 숲·강·역무실 27개의 표시된 선택지를 각각 별도 저장 복사본에서 GameService로 실행한다. 사진의 빵 들기와 수량 불변성, 중복 요청·위조 ID 거부도 확인한다.

기존 탐색·물건 조작·휴대 용기·생존 경로를 포함한 관련 테스트 57개와 TypeScript 빌드가 통과했다. 동점 기준이 명시되면서 달라진 보조 선택 순서는 현재 표시되는 경로를 따르도록 테스트를 갱신했다.

384×824 브라우저에서 같은 저장 순서 변경을 거쳐 계산대의 빵 들기를 실행했다. 독백 다음에 실행 결과가 이어지고 손에 든 물건의 선택지로 전환됐으며, 오류 알림·콘솔 오류·가로 넘침이 없었다. 행동 요청은 한 번, 실제 Gemini 호출은 0회였고 빵 수량 2개도 유지됐다.
